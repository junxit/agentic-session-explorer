Changelog
=========

0.8.0
-----
sx now supports Pi and its fork Oh My Pi: their sessions can be browsed,
exported, deleted, moved to a new project directory and cleaned up like any
other harness's. Most of the fixes below came out of an adversarial review of
the delete, move and cleanup code, and several of them affect every harness.

Pi and Oh My Pi
- New adapters for Pi (`pi`, npm @earendil-works/pi-coding-agent 1.5.0) and
  Oh My Pi (`omp` 18.15.0). Both were built from each harness's source code;
  no real sessions were sampled, so the README marks them "from source".
- Branched sessions. Both harnesses keep every retried or edited prompt in the
  same file. In the viewer, `t` cycles between the current branch (with a
  count of what the other branches hold), the current branch followed by every
  other branch, and the whole tree in the order it was written. `e` asks which
  of the three to export.
- A Pi delete removes the transcript only, as Pi's own delete does. An Oh My
  Pi delete removes what Oh My Pi's own delete removes: the transcript, its
  artifacts folder and every S.jsonl.*.bak backup, plus any rewrite temp file
  older than five minutes. The backups go first and the delete stops at the
  first failure, so a backup never outlives its transcript. Nothing is deleted
  while the transcript is missing, lock files beside a transcript are never
  removed, and Oh My Pi's shared stores (history.db, stats.db, pins, blobs/)
  are left alone.
- A move re-points the session header and relocates the transcript into the
  folder the new path encodes to. Pi forks that link to a moved transcript are
  re-pointed at its new location.
- A file sx cannot read or recognize is listed as "(unrecognized format)
  <file name>" and can be browsed, but is never deleted, moved or offered for
  cleanup; `sx harnesses` counts such files. Only the debris the harnesses
  leave is offered, as a fragment: an empty file, or one whose first line is
  an entry the harness writes, and for Oh My Pi only under its own
  <time>_<id>.jsonl name. A damaged first line makes the file unrecognized.
- A session in a format sx does not know (a format version it has not seen,
  or an Oh My Pi file that begins neither with a 256-byte title slot and the
  header nor, as older ones do, with the header) is refused for a delete as
  well as a move, and makes its project unknown, so its folder is never
  offered as a dead project's.
- A transcript reached through a symlinked project folder, or as a linked
  file, is listed once. Nothing is deleted or moved through a project folder
  that is a symbolic link.
- `sx harnesses` shows where each store was found and any warnings about it.
  The other commands print the warnings to stderr, and the TUI lists them at
  the top of the tree. A harness that handed its store to the other one shows
  as "store belongs to Oh My Pi" (or Pi), in `sx harnesses` and in the TUI.

Where their stores are
- Pi's PI_CODING_AGENT_DIR is read the way Pi reads it: nothing is trimmed,
  `~/x` and `~//x` are joined onto the home directory as Node's path.join
  joins them, and a file:// URL becomes the path it names. A relative value is
  ignored with a warning, as are the home directory and `/`.
- Oh My Pi reads PI_CODING_AGENT_DIR without `~` expansion, and ignores it
  while a profile is set. Profiles (OMP_PROFILE beats PI_PROFILE),
  PI_CONFIG_DIR (a directory name under home), and XDG_DATA_HOME and
  XDG_STATE_HOME (only when <xdg>/omp already exists) are followed.
- sx also reads the .env files Oh My Pi reads at startup (~/.env,
  <config root>/.env and <agent dir>/.env, and a session's project .env when
  it checks that session's lease) for the variables Oh My Pi takes from them.
  They are parsed as Bun's util.parseEnv parses them, Bun being Oh My Pi's
  runtime, and the store location follows that reading. They are parsed as
  Node's util.parseEnv parses them too: where the two read a followed
  variable differently (`KEY: value`, `KEY` then `=value` on the next line, a
  byte-order mark, `export<TAB>KEY`, a carriage-return line break, `=KEY=v`),
  every lease counts as unknown, so every Oh My Pi session counts as open,
  with a warning. In a project's own .env, a disagreement makes only that
  project's sessions unknown, with no warning.
- A .env file sx cannot read the way Oh My Pi does (over 1 MiB, not a regular
  file, or not readable) makes the leases it could move unknown, so those
  sessions count as open. PI_TEST_SESSION_OWNERS_DIR is honored, and
  PI_TEST_RUNTIME is mirrored as Oh My Pi handles it.
- When both harnesses point at one store, it belongs to whichever harness the
  store's own marks point to. Files only Oh My Pi creates in the agent
  directory, or, among the sessions, a transcript or crash backup that starts
  with Oh My Pi's title slot or an artifacts folder named for a transcript,
  make it Oh My Pi's; otherwise it is Pi's. A file name alone, a backup's or a
  lock file's, is not evidence. The other harness lists nothing there, and
  says why.
- Not listed: custom session directories (--session-dir,
  PI_CODING_AGENT_SESSION_DIR, Pi's sessionDir setting) and other Oh My Pi
  profiles' sessions, with a warning wherever sx can tell; and Oh My Pi's gc
  archives (archive/sessions/*.jsonl.gz), which sx never touches.

Open sessions
- Pi marks no open session at all. Oh My Pi holds a lease on a session only
  while it writes to it: sx asks the kernel whether that lock is held
  (F_GETLK, on macOS) and never takes it. It checks every lease directory it
  knows of, and counts finding none beside existing sessions as "cannot
  tell", which means open.
- On macOS sx also lists your own processes that look like Oh My Pi (`omp` or
  `oh-my-pi` in the command line, from ps) and what they have open (lsof). An
  open <id>.lock counts as held wherever Oh My Pi keeps it, and its directory
  becomes one more place sx checks. If Oh My Pi is running and its open files
  cannot be listed, or the process list cannot be read, a session that would
  read free counts as unknown, which means open. An Oh My Pi running under
  another name, as another user or inside a container is not seen by this
  scan, but the lease-directory checks still apply. lsof runs with -b, which
  keeps it off the calls that can hang on an unresponsive mount, and in a
  UTF-8 locale; the names it escapes are decoded.
- The live badge reuses its process scan for 5 seconds from when the scan
  finished, and the store and .env readings for 5 seconds too. When it has to
  scan again, ps and lsof get one second each, and a timeout counts as "cannot
  tell", which shows as live. Every delete and move scans and reads afresh.
- On Linux Oh My Pi's lease is an abstract socket sx cannot check, so every
  Oh My Pi session counts as open there: browse and export only. The same
  holds on every other platform but macOS.
- A session that is open but idle cannot be detected, so both harnesses'
  delete and move confirmations say to close the session in the harness first.
  Otherwise Pi's next turn fails, or is written to a file Pi never lists, and
  Oh My Pi's next write can bring a deleted session back whole, leave a moved
  one in two places, or leave a header-less file.

Deleting
- Liveness is checked again right before a delete runs. A session that went
  live after the dialog opened, and so was confirmed without the typed DELETE,
  is not deleted; pressing `d` again asks for the phrase.
- A path that cannot be checked is reported as refused and never removed.
  0.7.0 reported it as "does not exist", as if it were already gone.
- The last-session checkbox comes with a list of the paths it removes, per
  harness, and what each holds. Right before removing them, sx counts the
  project's sessions again from a fresh scan of every harness, Pi and Oh My Pi
  check their folders again, and nothing is removed if the session's
  transcript was not deleted; 0.7.0 removed the project state even then.
- A delete that removed some paths but refused others warns which ones
  stayed.
- A session whose file disappeared while its dialog was open is reported as
  gone, and nothing is exported or deleted.

Orphan cleanup, every harness
- Each orphan is fingerprinted when it is listed. At deletion, anything that
  changed since then, was written in the last 90 seconds, or left the store is
  refused, and each harness asks its own question again: is the project still
  gone, is the folder still empty?
- "Cannot check" never means "gone": only "no such file or directory" makes a
  recorded project missing. A permission error, a dangling link or an
  unmounted volume leaves it unknown, and an unknown project is never an
  orphan.
- A Claude folder shared by colliding project paths belongs to a dead project
  only if every project in it is gone. 0.7.0 let the first readable session
  decide.
- A Pi folder with no sessions is offered only after 24 hours without writes,
  because Pi creates it as soon as it starts in a project, and its listing
  warns that a Pi running in that project fails its next prompt once the
  folder is gone.
- Orphan confirmations show each harness's open-session warning.
- Claude's scratchpads under /private/tmp/claude-<uid> are no longer offered
  as orphans, and the last-session cleanup no longer removes a project's
  scratchpad folder. That directory follows the user id, not the config home,
  so every Claude config on the account shares it: 0.7.0 offered another
  config's scratchpads as stale, an open session's included, whenever the
  config sx read did not know their sessions. A deleted session's own
  scratchpad still goes with it.
- Claude's other stale artifacts (file history, environment, task and
  security state) are offered only when every project folder could be read,
  so a session out of sight never looks deleted. A permission error counts as
  out of sight, and so does a projects store or a project folder behind a
  link that dangles (an unmounted volume, say) or leads to something other
  than a directory. The same check runs again at deletion time.
- One orphan that removes more than one path needs the typed DELETE <n>, as
  deleting every orphan does. Stale artifacts are grouped a class at a time,
  so a single row can hold many directories, and 0.7.0 confirmed it with a
  plain Enter.
- An orphan delete is limited to the paths its confirmation previewed as
  removable, each still checked again. A path the dialog showed as refused
  stays refused, even if its reason lapses while you type the phrase (the
  90-second window, for example), for one orphan and for every orphan alike.
  What stays is named in the toast with its reason, recorded in the op-log,
  and keeps its row. Deleting every orphan lists the paths that will be
  refused inside otherwise deletable orphans, and counts the orphans the
  dialog does not show.
- An orphan delete that the op-log could not record says so, as session
  deletes already did.

Moving (Claude, Pi and Oh My Pi)
- A move runs as units: a whole folder, or one session with its sidecars.
  Each unit's rewrites and renames succeed together or are put back, Ctrl-C
  included, and reported as refused. Planning accounts for folders created
  earlier in the same move, and each unit is checked again right before it
  runs.
- Nothing is ever nested inside a folder that appeared in the meantime; it is
  merged into instead. Nothing is moved into a destination folder that is a
  symbolic link. A rename across file systems is refused rather than done as
  a copy. When a later step of the same move carries a transcript again, the
  result still says where it ended up.
- A move that changes only the letter case of a path renames the folder in
  place on a case-insensitive file system (APFS by default).
- Re-running the same `sx move` finishes an interrupted one, Oh My Pi memory
  it left behind included, even when no session remains to move. For Pi and
  Oh My Pi it also removes a second hard link a crash left in the old folder.
- Pi fork links of the units that finished are re-pointed even when a move is
  interrupted or fails part-way. A re-run repairs fork links an interrupted
  run left dangling whenever a Pi session takes part in it, even with nothing
  left to relocate. Links left by a run killed outright after its last
  relocation, with no Pi session left under the old path, are not repaired.
- The op-log records a move step by step: `move_started` with the plan, one
  `move_unit` per unit (status `done`, `partial`, `refused` or
  `nothing to do`), and `move_sessions` with `status` (`finished` or
  `interrupted`) and `relocated`. After a Ctrl-C, or an error, the records say
  what the move had done by then, the Pi fork links it re-pointed on its way
  out included.
- `sx move` exits 1 when anything was refused, not only when everything was,
  and `sx move --dry-run` exits 1 when its preview shows anything that would
  be refused (0 for a clean preview).
- A Claude project folder shared with a colliding project path is no longer
  moved whole when one of them moves; its sessions move individually. A
  transcript that recorded some other directory first still travels with its
  folder, as it did in 0.7.0: only true path collisions stay behind.
- Oh My Pi: `additionalDirectories` follows Oh My Pi's own moveTo (the new
  cwd is filtered out and an empty list is dropped; nothing is re-pointed),
  and `previousSessionFiles` gains the old location. A session's artifacts
  folder and backups move with it, or nothing of it does; sx moves the backups
  on purpose, so Oh My Pi cannot restore the session in the old folder. The
  project's memory folder moves too, ahead of the sessions, unless another
  project's sessions share it, some of the project's sessions stay behind, or
  it was written in the last 90 seconds. Memory folders are planned as
  project folders are, so in a chained move each is vacated before another
  takes its name, and two that would trade names stay put. Lock files stay
  where they are, and leftover backups or drafts in a folder make its
  sessions move one by one.
- The TUI plans from a fresh scan before the preview and again before running.
  A session that went live after a confirmation given without the typed
  phrase is refused, in the TUI and at `sx move`'s y/N prompt.
- The live-session warning now says what really happens: moving a session its
  harness still has open breaks it. `--yes` still prints it.

Rewrites
- A rewritten line keeps every byte except the value that changed: number
  formats, escapes, spacing and CRLF line endings. A line sx cannot splice
  that way (one with a duplicate key, say) is written whole, compactly, as the
  harnesses write JSON. 0.7.0 rewrote every changed line whole, with a space
  after each `,` and `:`.
- So an inverse move now restores the transcripts it rewrote byte for byte in
  all but a few cases, which the README lists. Two are by design: Oh My Pi's
  `previousSessionFiles` grows and its `additionalDirectories` loses the new
  cwd, as Oh My Pi's own move does; and the inverse of a merge also moves the
  destination's pre-existing sessions, which the plan now says.
- A deeply nested line is skipped as malformed instead of aborting a scan.

TUI and CLI
- Export before delete starts on the whole tree for a branched session,
  whatever the viewer shows, says when the current branch is empty, and reads
  the session again when it runs.
- In both branch-view pickers the highlighted row is the choice, marked ● and
  ○ so it reads without color.
- For a branched session, `e` reads the session again after you pick a view,
  so the export holds everything written while the dialog was open.
- Opening a session no longer cancels an export, delete or move running in
  the background, and an action that is canceled says so.
- Text from session files cannot drive the terminal anywhere: `sx list`,
  `sx move`, `sx memory`, `sx harnesses`, every TUI label, preview, dialog and
  toast, and the headers of exported Markdown. C1 control characters are
  neutralized too: U+009B shows as ␛[.
- The session id in an export file name is made filename-safe. A `/` in one
  aborted the export, and with it the export before a delete. Exporting a
  session whose file is gone writes nothing.
- The delete dialog fits on short terminals and opens on its heading, at
  80×24 too: the preview shrinks so the controls stay in view, and the
  warnings wrap.
- A dialog is dismissed only once, so two quick Enters cannot close the
  screen beneath it as well.

Testing
- A test that runs for 120 seconds is taken for a hang: the run stops with
  exit status 1, naming the test and printing every thread's stack.
  SX_TEST_TIMEOUT changes the limit; 0 turns the guard off.
- All 1634 tests pass on Python 3.15, including with every warning promoted
  to an error.

0.7.0
-----
sx now requires Python 3.15 or newer, and every dependency is pinned to an
exact version.

Upgrading from 0.6.x on Python 3.13 or 3.14
- A plain `uv tool upgrade sx` stops with "the current Python version … does
  not satisfy Python>=3.15": the tool's environment was built on the older
  interpreter, and uv does not change interpreters on its own. Run
  `uv tool upgrade sx --python 3.15` once; plain upgrades work again after
  that. The update notice in 0.6.1 and earlier still suggests the plain
  command, and released code cannot be changed after the fact.
- Fresh installs need nothing extra. `uv tool install` and `uvx` download
  Python 3.15 themselves when no compatible interpreter is present.

Dependencies are pinned
- textual 8.2.8 and rich 15.0.0 are exact pins rather than open-ended minimums,
  so a future Textual major release cannot reach a new install before it has
  been tested here. Textual 8.2.8 also fixes a crash when clicking a screen's
  padding and the parsing of multi-codepoint Kitty keys.
- The build backend (hatchling 1.32.4) and the development tools (pytest 9.1.1,
  pytest-asyncio 1.4.0, ruff 0.17.1) are pinned too. ruff joins the dev extra,
  so `uv run ruff check` lints with the same version everywhere, and a
  .python-version file selects 3.15 for development.
- uv.lock is refreshed to current releases. None of the previous versions had a
  known vulnerability; this is maintenance, not a security fix.
- Dependabot now watches uv.lock weekly and opens security updates.

Lint
- The tree is clean under ruff 0.17.1: imports sorted, unused imports removed,
  collections.abc.Iterator instead of typing.Iterator, Textual BINDINGS
  annotated as ClassVar. No behavior changed. The four deliberate catch-all
  handlers — one adapter's failure must not abort a whole scan — now carry an
  explicit S112 exemption alongside their existing one.

Testing
- All 213 tests pass on Python 3.15, including with deprecation warnings
  promoted to errors.

0.6.1
-----
sx now follows Claude Code to a relocated configuration home.

Claude Code lets you move its configuration directory with the
CLAUDE_CONFIG_DIR environment variable. sx assumed ~/.claude unconditionally,
so anyone who had set it was browsing the wrong store — an empty or stale one —
while the delete and move cascades aimed at paths the harness no longer writes
to. sx now resolves the store the way the harness does, and every derived path
follows: the projects store, the cascade directories, security state,
history.jsonl, project memory and the orphan scan.

The subtle part is .claude.json. It moves *into* the configuration directory
when the variable is set, and sits beside ~/.claude when it is not, so it is
derived separately rather than from the config directory — the obvious
simplification would have broken the default path for everyone. The
/private/tmp/claude-<uid> scratchpad tree does not move, because Claude derives
it from the uid.

Resolution is strict. A directory that does not exist reports Claude as not
installed rather than quietly falling back, so sx can never read or delete from
a store it was not pointed at. A value that is relative, the home directory or
a filesystem root is ignored with a warning instead: Claude Code requires an
absolute path too, and honoring a relative one would make the delete allowlist
depend on the working directory. User-facing labels name the directory actually
in use, so an orphan row can no longer offer to clean "~/.claude/tasks" while
pointing somewhere else.

The test suite now scrubs CLAUDE_CONFIG_DIR for every test. Without that, the
suite's correctness would depend on the developer's own shell — a contributor
with a relocated install would have had a move test rewrite their live config.

0.6.0
-----
Delete now finishes the job, and project memory gets a home of its own.

Deleting a session used to leave most of what the harness wrote beside it. An
audit of the real stores found the backlog that had built up: 350 orphaned
session-env directories, 70 file-history directories, 15 scratchpads, 8 task
directories, 10 security-state files and 633 prompt-history rows, all belonging
to conversations that were deleted long ago.

Every artifact a session owns now goes with it
- ~/.claude/session-env/<session-id>/ and ~/.claude/tasks/<session-id>/.
- ~/.claude/security/security_warnings_state_<session-id>.{json,lock}. The id
  sits in the middle of the filename, so the old prefix search never saw them.
- /private/tmp/claude-<uid>/<encoded-project>/<session-id>/ — the scratchpad,
  keyed by both project and session, outside every store root until now.
- Prompt-history rows in ~/.claude/history.jsonl and ~/.codex/history.jsonl,
  removed through the atomic rewriter added in 0.5.0, so a harness appending
  mid-rewrite cannot lose turns.

Cascade targets are now constructed from the session id rather than searched
for by prefix, and a final check refuses any target whose name does not contain
that id. There is no pattern left that could widen onto a neighbour.

Project memory is never collateral
- A harness writes memory to outlive the conversation that produced it, so no
  session delete removes it. Every delete preview states how many memory files
  the project has and that they are being kept.
- Deleting the LAST session for a project — counted across every harness, not
  just the one you are looking at — offers an extra, unticked checkbox to remove
  the project's own state as well: memory, store folder, the ~/.claude.json
  settings entry, Gemini's folder-trust entry (whose key is lower-cased, which
  an exact match had been silently missing) and its prompt-history rows.
- New `n` key and `sx memory` command browse, export and delete memory
  directly. Each document lists its type, size and the session that wrote it:
  memory records an originSessionId, so sx can show which memories have outlived
  the conversation they came from. Memory removal is logged under its own
  op-log action, never folded into a session delete.

The backlog is visible instead of assumed
- The orphan screen reports artifacts belonging to sessions that no longer
  exist, grouped one row per class — 350 separate rows would have buried every
  other finding.

Guard changes
- ~/.claude is deliberately NOT a store root. The directories the cascade needs
  are named one at a time, so plugins, settings.json, .credentials.json and a
  282 MB vendored virtualenv stay outside the guard entirely.
- `security/` has to be a root to reach the state files, so a new
  `protected_paths()` hook refuses the virtualenv and the harness logs inside
  it. Nothing in the calling code could reach them; this makes that a guarantee.

Noted while auditing, deliberately not acted on
- ~/.claude/plans/*.md are referenced by 56 of 62 transcripts, but only by
  filename inside prose, and a plan outlives its session much as memory does.
- ~/.claude/paste-cache/*.txt is hash-named and only 3 of 30 appear in any
  transcript — too weak a link to delete on.
- Of the four legacy cascade directories, only file-history ever matches: shell
  snapshots are epoch-named, sessions/ is PID-named, and all 41 todos entries
  are <agent-id>-agent-<agent-id>.json. They are kept, and the code now says so
  rather than leaving the next reader to assume they work.

Testing
- 35 new tests. Fixed an isolation leak the memory module introduced: sx.memory
  resolves `home` in its own namespace, so patching an adapter's home did not
  cover it and a TUI test read the developer's real ~/.claude. There is now a
  regression test for exactly that.

0.5.1
-----
- The `M` key (move the project directory, then re-point its sessions) is shown
  in the footer. It was hidden, following the pattern of the vim-style
  navigation aliases j/k/g/G/tab — but those only duplicate the arrow keys,
  whereas `M` is a primary action and the more consequential of the two move
  keys, since it moves a real directory on disk rather than only session
  records. Hiding it left the riskier key as the undiscoverable one. The footer
  now reads "m Move" and "M Move dir".

0.5.0
-----
Move a project to a new directory. When you relocate a repo, every harness keeps
pointing at the old path: the sessions group under a directory that no longer
exists, get flagged as orphans, and the only thing sx offered was deletion. Now
there is an inverse of delete.

- `m` re-points the highlighted session's project at a new directory, for when
  you have already moved it by hand. `M` moves the project directory itself
  first, then does the same. `sx move --from PATH --to PATH [--relocate]` does
  either from the shell, with `--dry-run` to see the plan and stop.
- One move covers every harness holding sessions at that path. Claude re-points
  the `cwd` recorded throughout each transcript and then moves the project
  folder to the name the new path encodes to, carrying `memory/` and each
  session's `<session-id>/` sidecar with it. Codex re-points the `cwd` in its
  `session_meta` and every `turn_context`. Gemini rewrites the `.project_root`
  marker and re-keys `projects.json`. opencode updates the session's `directory`
  and `path` columns and its workspace, in one transaction.
- Only the structural working-directory field is rewritten. A path mentioned in
  tool output or in your own prose is historical record and is left as written.
  Matching is boundary-aware, so moving `proj` carries `proj/docs` along and
  leaves `proj-old` alone.
- A move is reversible: running it in reverse restores the previous state byte
  for byte, and the op-log records both endpoints so the old path stays readable
  afterwards. Moves are logged alongside deletions in `sx-deletions.log`.
- Nothing is overwritten. If the harness has already run at the new path the
  stores are merged entry by entry and any colliding name is refused, with the
  refusal shown in the confirmation rather than discovered afterwards.
- Rewrites are atomic: a new copy is written beside the original and swapped in,
  lines that cannot be parsed are copied through byte for byte (the tolerant
  JSONL reader drops them, which would have silently deleted every
  partially-written record), and the write is abandoned if the harness appended
  to the file while it was in progress.
- Re-pointing Claude's own project state is opt-in — `--claude-config`, or the
  checkbox in the dialog — covering the `~/.claude.json` `projects` entry (trust
  decision, `allowedTools`, MCP servers) and `~/.claude/history.jsonl`. Off by
  default because those files belong to a harness that may be running; the write
  is abandoned if either changes underneath it. Existing settings at the
  destination are never merged over.
- Moving the project directory itself refuses a destination that already holds
  anything, a destination inside the source, the home directory, and any
  directory containing a harness store. It runs before the stores are touched,
  so a failure leaves everything as it was. A cross-filesystem move is disclosed
  as the copy-then-delete it really is.
- opencode's shared `project.worktree` is deliberately never rewritten — a
  project row is shared with sessions that were not part of the move — and the
  plan says so instead of quietly skipping it.
- Grouping moved from `m` to `b` to make room for the move keys.

Two fixes found along the way

- Every keybinding was dead at startup. Textual focused the filter Input, which
  its CSS hides but which still received keys, so typing `o`, `e`, `d`, `r` did
  nothing except silently fill an invisible filter box. The tree now takes focus
  on mount.
- Deleting a Claude session left its `<session-id>/` directory (sub-agent
  transcripts, tool results) behind, unattributable to anything. It is now part
  of the session's correlated paths, so it is both disclosed in the delete
  preview and removed with the session.

0.4.0
-----
Safety, correctness and hardening pass. The theme: sx must never claim to have
done something it did not do, nor destroy more than its confirmation disclosed.

Deletion now tells the truth
- Delete previews and notifications report database-row removals (DeleteResult
  .note), which were previously invisible: an opencode session without a sidecar
  previewed as "Nothing to remove · 0 B" and then destroyed the whole
  conversation.
- Refused deletions are no longer reported as successes. The orphan row stays,
  the message is an error, and partial results are stated honestly. Previously a
  fully-refused bulk cleanup showed "Deleted all orphans · freed 0 B".
- Gemini's stray temp files are actually deletable: find_orphans reported paths
  outside the adapter's own store roots, so the guard refused all of them.
- Bulk orphan confirmation dry-runs each target instead of summing reported
  sizes, so the promised total matches what the guard will allow.

Deletion no longer destroys more than it discloses
- Confirmations enumerate what a folder contains (files, nested transcripts,
  memory files) before it is recursively removed.
- "Empty" project folders now state what remains instead of claiming to hold
  nothing while containing scripts, tool output or nested transcripts.
- Cascade deletion matches session ids exactly (UUID-shaped) rather than by
  substring; a session file named "a.jsonl" previously swept every ~/.claude
  state entry containing the letter "a".
- Markdown export never overwrites: colliding names get a suffix, so
  export-before-delete cannot destroy the archive it just wrote.
- A project on an unmounted volume is "unavailable", not a dead-project orphan.
- A folder's status is judged from all its sessions, and the lossy folder-name
  decode is no longer trusted to declare a project dead.
- opencode deletes database rows first and unlinks the sidecar only on success,
  removing three partial-delete paths.
- The live-session guard asks the adapter for its own activity signal (opencode
  uses the database column), and treats "unknown" as live.

Hardening
- Terminal control sequences in transcripts are replaced with visible glyphs in
  the TUI and in exports, so hostile chat content cannot retitle a window, write
  the clipboard, or clear the screen when viewed.
- Orphan table cells are Text objects: reasons embed untrusted paths, which
  Textual would otherwise parse as markup (and malformed markup wedged the
  screen).
- opencode session ids are validated before being used to build a file path.
- The delete guard refuses a store root itself.
- The op-log moved to ~/.local/state/sx/ (SX_LOG_FILE overrides), is owner-only,
  and write failures are surfaced instead of silently swallowed.

Robustness and performance
- `sx update` no longer crashes on a corrupt (non-dict) cache file; failed
  version lookups are cached so the daily throttle works; responses are bounded;
  `sx list` shows the update notice too.
- Gemini discovery no longer replays entire chat files to count messages.
- Liveness badges are briefly cached, so filtering does not stat every session
  on each keystroke.
- Runtime guards replaced asserts (stripped under `python -O`) and unguarded
  adapter lookups that could tear down the app mid-deletion.
- 21 new regression tests, including the previously impossible case of an
  adapter that refuses its own reported orphans, plus a cross-adapter invariant
  that every orphan path is deletable by its own guard. Tests no longer read the
  developer's real session stores.

0.3.0
-----
- opencode is now a fully-supported harness (browse + orphan-detect + delete).
  Unlike the file-per-session harnesses, opencode stores every session as rows
  in a shared SQLite database (~/.local/share/opencode/opencode.db). The new
  OpencodeAdapter reads sessions read-only (WAL-safe) and deletes a session by
  removing only its rows (session/message/part/todo/share) plus its
  session_diff sidecar — never the database file, never another session, and
  leaving the shared log/ files alone.
- DeleteResult gains an additive `note` field so the op-log records non-file
  removals (e.g. "deleted 8 db rows"); shown for opencode deletes.
